按理想恒定角减速度 0.15 rad/s² 计算，0.3 rad/s 停下来还需约 17.2°，尚未计入通信与执行延迟。因此，不能把它作为末端不准的直接修复。
推荐开阔区允许更灵活的运行朝向，窄通道按车体扫掠限制朝向，最终槽位仍按任务标准验收。
仿真与实车验收
- 仿真：启动延迟、单车速度偏低、位置抖动、TEB 放弃、旧命令延迟到达、终点超调。
- 单车：长路径、短路径、横移、末端转向、受控暂停恢复。
- 三车：快慢不同但不追尾、不互相争抢通道。
- 十车：先验证静态五阶段基线，不加入突然动态障碍。
通过条件包括：唯一有效速度来源、无旧版本命令、末端不持续抖动、无误报成功，以及真实终点满足冻结标准。正常路径中非必要启停、恢复次数应与 P1 基线比较，不能只看平均完成时间。
七、阶段 P4：引入滚动协同规划
推荐采用有界的优先级/冲突搜索 + 滚动更新路径，不首先做十车全量连续联合 MPC。
原因是当前主要瓶颈仍包含状态可信度、执行一致性和调度状态复杂度。先采用可解释、可设置计算预算的方案更容易落地。
1. VM 的新增职责
每车上报：
- 位姿、速度、时间戳、定位质量；
- 当前实际路径进度；
- 当前控制模式、停车能力和故障；
- 已接受的路径版本与占用；
- 局部障碍观测及有效时间。
VM 每次规划：
1. 保留车辆已经承诺执行、且停车必需的路径范围。
2. 更新当前占用与障碍。
3. 只重新规划尚未承诺的后续部分。
4. 先解决当前冲突组，再保留无冲突车辆的原计划。
5. 新计划经相关车辆确认后生效。
6. 未确认、信息过期或计算超时，保持已有安全计划或停车。
路径预留不能仅因计时结束而释放；必须确认车辆实际离开。失联车辆也不能从占用图上消失。
可以借鉴 RHCR 的滚动窗口思想，但其离散多智能体求解不能直接保证连续实车安全，代码集成前还需检查许可证及模型适配。
规划周期、窗口长度不现在拍定：根据 P2 的延迟、停车时间和 VM 实测计算时间确定。控制与停车必须能在规划超时情况下独立工作。
2. 动态障碍的数据链要先拆分
当前定位和导航都使用队友过滤后的扫描，见 [robot_navigation.launch (line 35)](/Users/zhangmiaohan/Maomi/NKUworkshop/jetauto_swarm_wrc/jetauto_multi/launch/fleet_vendor_omni/include/robot_navigation.launch:35)。动态场景下不能继续默认“一份过滤扫描满足所有用途”。
推荐：
- 定位输入：可谨慎去除高置信度队友影响。
- 导航输入：保留队友及未知障碍的真实占用。
- 近场停车输入：尽可能直接使用新鲜传感器，不依赖远程队友位置才能发现危险。
- 过滤时使用对应扫描时刻的状态；关联不确定时保留障碍。
- 跟踪结果过期后增大不确定性或停车，不能把目标直接当作消失。
obstacle_detector 可作为 ROS1 障碍提取与跟踪候选，但应先验证 Melodic 构建、算力、遮挡表现和雷达适配，不预设它一定可直接部署。
3. 推荐的行为选择顺序
1. 有碰撞风险：立即停车。
2. 障碍正在短暂横穿：等待。
3. 存在安全局部绕行：申请并执行新路径。
4. 当前编队过宽：选择已经验证过的窄队形或分批通过。
5. 没有安全前进路线：仅在后方空间已验证时退让。
6. 仍无解：明确报告受阻，不无限重试。
换队形不仅检查最终槽位，还要检查转换过程的完整路径；增加切换成本和稳定保持规则，防止在两种队形之间反复切换。
4. 本地停车是动态实车测试的前置条件
需要新增并单独验收：
- 车端命令有效期；
- 失联、命令中断后的停车行为；
- 覆盖运动方向的感知与停车距离；
- 旧连接恢复后不执行积压命令。
软件停车不能替代实体急停。对横移、倒车尤其要核验当前雷达裁剪后的视野；看不到且不能安全制动的方向，应限制运动。
P4 验证顺序
子阶段	仿真	实车
影子规划	生成新方案但不控制，检查冲突与计算预算	VM 只监测并出建议，原执行器运行
静态滚动规划	单车延迟、堵路、冲突交换、无解场景	三车后十车，固定障碍
动态等待/绕行	横穿、突然停止、跟踪丢失、规划超时	从单车受控软障碍开始，再三车
自主换队形	窄通道、队形转换冲突、反复障碍	已验证场地内，最后才上十车
故障降级	断网、定位跳变、车端失联	先台架；停车能力通过后才进行低速受控测试


应分别验收：
- 有解场景：安全完成；
- 无解场景：安全等待或退出；
- 故障场景：正确停车并保留占用。
不能要求所有场景都显示 SUCCEEDED。
八、阶段 P5：十车部署与最终验收
发布顺序
每个阶段形成一个可回退版本：
1. 相关静态检查与契约测试。
2. 对应有界闭环仿真。
3. 单车实车。
4. 三车交互。
5. 十车静态任务。
6. 十车动态扩展任务。
每次实车运行都遵循现有流程：底层检查无 FAIL → 关闭运动时 READY → 人员、场地与实体急停确认 → 才开启运动。
涉及 IMU/EKF 等底层启动参数时重启相应进程，不假设热更新。涉及厂商代码或新增车端安全机制时，另行明确授权。
最终通过标准
维度	验收要求
功能	十车完整基线任务一次连续完成，不靠中途重启跳过失败
精度	各阶段真实终点满足冻结的位置、朝向标准；同时报告 AMCL 估计值
安全	无接触、无未经批准的路径越界；净空包含实测误差和停车预算
控制	无控制权重叠、过期命令、超调假成功、无限末端修复
协同	局部问题不无故取消无冲突车辆；共同危险正确停车
动态行为	分别验证等待、绕行、换队形及无解退出
可追溯	每次任务保留版本、参数、完整失败记录和外部测量


建议将冻结版本下十次连续完整基线通过作为第一轮工程发布门槛；动态场景另按场景重复验证。这不是“成功率已经达到某个统计置信度”的证明，不能把调参中的失败删除后再计算成功率。
回退必须先停车、撤销控制权，再回到上一阶段已验收版本；不能在车辆运动中切换配置和控制器。
最终推荐
实施优先级应固定为：
P0 可追溯基线 → P1 确定性错误 → P2 真实能力与仿真标定 → P3 统一执行 → P4 滚动协同 → P5 十车发布。
不建议优先做三件事：全队提高角速度、全局放宽朝向、再加一个根据 AMCL 自动纠偏的独立程序。
这份计划按仓库架构审查和实验规划要求，将每个改动对应到证据、测试和准入门槛。当前尚未确定、必须通过后续测试解决的关键项只有四类：**有效运动反馈、真实定位与停车误差、TEB 发布前的路径约束能力、车端失联停车能力。**这些条件通过后，滚动协同规划才有可靠的执行基础。
